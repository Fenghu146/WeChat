## 二、发现并修复的缺陷

| # | 级别 | 缺陷 | 证据 | 修复 |
|---|---|---|---|---|
| 1 | 严重 | **加载失败却清空现有数据**：`loadFromFile` 无条件 `groups_ = std::move(loaded)`。存档为空/被截断/只有垃圾行时，6 个官方预置群被静默清空，且析构时把空目录写回存档 —— 数据永久丢失 | 写入 `not-a-record\n` 后 `setPersistencePath` 返回 true 且 `groupCount()==0` | 无可用记录时返回 false 并保持现状（预置群仍在）；好友注册表同样：文件有内容但一条都解析不出来时保持现状 |
| 2 | 严重 | **“原子写”既不原子又谎报成功**：直接以 `trunc` 打开目标文件写入，中途失败即损坏存档；且只检查 `!out` 就 `return true`。MinGW/libstdc++ 上打开**不存在目录**的路径会报告成功（`open_ok=1`），随后写入全部静默失败 | 对不存在的目录调用 `saveToFile` 返回 true（实测探针：流状态为 good，而文件根本不存在） | 新增 `persist_util_fh::AtomicWriterFH`：先写 `<path>.tmp` → flush/close 校验 → `rename` 替换；任一步失败返回 false 且保留原存档。群/好友/开通情况三处存档统一使用 |
| 3 | 中 | 存档数值字段无校验：`std::stoul(f[5])` 把 `-5` 回绕成天文数字（等于“群人数无上限”）；消息类型 `std::stoi` 后直接 `static_cast`，越界值进入业务 | 构造含 `-5` / `abc` / `99` 的存档 | 新增 `parseInt10` / `parseCount` / `parseKind` 严格解析：空群号、重复群号、人数上限非 1~100000、类型越界一律丢弃该记录 |
| 4 | 中 | 同一群号的重复记录不合并：第二条永远无法被 `findGroup` 命中，却会被反复写回存档 | 两条相同 `1007` 记录 → `groupCount()==2`，仅一条可访问 | 载入时按群号去重（取首条） |
| 5 | 中 | 成员/管理员号码以 `,` 连接且不转义：号码本身含 `,` 时往返后被拆成两个成员 | 号码 `a,b` → 载入后 `memberIds.size()==2` | `joinIds` / `splitIds` 增加 `\` 转义与反转义 |
| 6 | 中 | CRLF 存档不兼容：行尾 `\r` 留在最后一个字段中 | 行尾成员号变成 `20002\r`，与业务值失配 | `splitFieldsFH` 统一丢弃行尾 `\r`（所有存档解析共用） |
| 7 | 中 | 开通情况“只增不减”：`loadActivatedFromFile` 只做 `addActivated` | 把微博从存档删掉后重启，仍显示已开通 | 载入前先清空各档案的开通集合，再按存档重建 |
| 8 | 中 | 撤回时间窗**先赋值后校验**：传负数时抛异常（且异常从 `bool` 接口逃逸），并且非法值 `-1` 已写入配置，导致之后所有消息都无法撤回 | `setRecallTimeLimit(admin, seconds(-1))` → 配置被污染为 -1 | 先校验后赋值，非法值返回 false 且配置保持原值；构造期非法配置仍抛异常（保持既有契约） |
| 9 | 中 | 单员禁言对管理员“返回成功但毫无效果”：发言校验用 `isPrivileged` 绕过了单员禁言 | 群主禁言管理员后，管理员仍可发言 | 单员禁言对所有角色生效（全员禁言对 ADMIN/OWNER 的豁免保持不变） |
| 10 | 低 | 同一群内消息标识可重复，按标识撤回会命中另一条消息 | 两次发送 `id="m1"` 均成功 | `sendMessage` 拒绝重复标识（并复核发送者一致性） |
| 11 | 低 | 群名/公告只校验“非空”，全空白可通过 | `editGroup(owner, "   ")` 返回 true | 新增 `isBlankText`，全空白视为空 |
| 12 | 低 | 越界消息类型被当作“支持” | `supportsKind(QQ, static_cast<MessageKindFH>(99)) == true` | 新增 `isValidKindFH` 并接入消息策略 |
| 13 | 低 | 双向好友只检查单向：存档残缺（只有 `b→a`）时 `makeFriends(a,b)` 会凭空添出重复关系；载入也不去重 | 预置 `b→a` 边后再加好友，边数多出 | `addBothWays` 检查反向边；载入时按（平台+方向）去重 |
| 14 | 低 | 预置群成员注入与文档承诺不符：判据是“当前是否为空”而非“是否注入过”，所有人退群后再次启动会被强行加回 | 二次调用返回 true 并重新塞回成员 | 记录“已注入过的群号”，使其真正幂等 |
| 15 | 中 | **切换平台模式后原 QQ 管理员保留微信模式下的特权**：`switchPolicy` 只换策略对象、成员表里的 ADMIN 身份原样保留，而微信钩子原先只收窄了 INVITE/SET_ALL_MUTE，导致切到微信模式后管理员仍能踢人/禁言/改群名/发公告/改群配置 —— 与任务书“微信群仅有群主为特权账号”及注册表层 `GroupRegistryFH::kickMember`（微信群仅群主）双重矛盾 | `switchPolicy(WeChatPolicyFH)` 后 `kickMember(admin, member)`、`editGroup(admin, ...)`、`setRecallTimeLimit(admin, ...)` 均返回 true | 微信平台钩子把公共步骤判为 ADMIN+ 的**全部管理动作**收窄为仅群主：`KICK_MEMBER`、`MUTE_MEMBER`、`EDIT_GROUP`、`PUBLISH_ANNOUNCEMENT`（连同原先的 `INVITE_MEMBER`、`SET_ALL_MUTE`）；由 EDIT_GROUP 授权的群配置变更因此也归群主。分两步落地：先收窄踢人/禁言（方案 A），再收窄改群名/发公告（方案 B，用户确认口径后执行） |

### 缺陷 2 的补充说明

原实现只判断 `if (!out) return false;`。在 MinGW/libstdc++ 上：

```cpp
std::ofstream o("no_such_dir_fh/sub/archive.dat", std::ios::binary | std::ios::trunc);
printf("open_ok=%d\n", (int)(bool)o);   // 实测输出 open_ok=1，而该文件/目录并不存在
```

即“流状态良好但一个字节都没写下去”，调用方会认为存档已写入。改为 write-then-rename 后，`rename` 的失败使 `saveToFile` 正确返回 false；同时“写一半失败”也不会再破坏上一版存档。

## 四、未改动项与观察（供后续决策）

1. **切换平台后的管理员权限（已按方案 B 全部收窄）**：把 QQ 群动态切换为微信模式后，原有管理员**不再享有任何管理特权**——踢人、禁言、改群名、发公告、变更群配置（撤回时间窗/成员邀请开关）一律仅群主可执行；模型层与注册表层口径完全一致，也与任务书“微信群仅有群主为特权账号”的措辞一致。原先把 `EDIT_GROUP` / `PUBLISH_ANNOUNCEMENT` 视为“平台无关的公共操作”的约定**已按本次口径决策废止**，`abstract_policy_test.cpp` 中相应用例同步改为平台差异用例（`SendIsCommonButGroupEditingIsPlatformGated`：发言两平台一致，改群名在微信群收窄为仅群主）。
2. **查询接口返回内部容器的指针/引用**：`findGroup` / `memberIdsOf` / `chatOf` / `groupsOfPlatform` 返回指向 `groups_` 元素的指针或引用，随后 `createGroup`（push_back）或 `disbandGroup`（erase）会使其悬空（迭代器失效类问题）。其中 `app/client_ui.cpp` 的“解散本群”路径已修复（原先解散成功后立刻读 `info->name` 拼提示，属真实悬空解引用）：现在先拷贝群名再解散，且 `runOfficialChat` 的 `groupId` 改为按值传递、`findOfficial` 处补了生命周期使用约定。**接口本身按值返回的重构在后续分支完成**（涉及 70+ 处调用点）。
3. `UserProfileFH::bindWeChat` / `addActivated` / `setOnline` 声明为 `noexcept`，但其内部会分配内存（`bad_alloc` 将直接 `terminate`）。
4. `GroupMembershipFH` 的默认构造可产生 `getUser()==nullptr` 的成员对象（4 参构造有非空校验，默认构造没有）。
5. 并发写入：单文件采用 write-then-rename，但仍无跨进程写锁，按“单机单实例”假设。
