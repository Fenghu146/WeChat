# 一、设计任务分析

## 1.1 题目与背景

本课程设计的题目是「模拟即时通信系统实现」。题目背景是：某公司的即时通信业务先后推出 QQ、微信、微博等微 X 产品，各产品既可以独立提供服务，又互相辉映关联；课程设计要求把这些产品**整合为一个统一的立体社交软件平台**，并完成设计、实现与验证。

本设计的核心问题是：**当多个产品的业务「大部分相同、少部分不同」时，如何用面向对象的方法组织代码，使相同部分只写一遍、不同部分可独立替换、新增产品时不必修改已有业务代码。** 这一问题贯穿全部需求：好友关系要按平台隔离、群管理规则因平台而异、开通与登录要在多产品之间联动。

## 1.2 系统功能描述

依据任务书，系统需要实现的功能可归纳为六类，整理如下。

| 功能项 | 具体要求 | 本设计的实现边界 |
|---|---|---|
| 用户基本信息 | 号码 ID、昵称、出生时间、T 龄（号码申请时间）、所在地、好友列表、群列表；QQ 与微博共享 ID，微信独立 ID 但可绑定 QQ | 全部实现；自然人用 `UserProfileFH` 建模，平台号码由其解析 |
| 好友管理 | 好友信息的添加、修改、删除、查询；查询微 X 之间各自的共同好友（如微信可添加 QQ 推荐好友） | 全部实现，含备注、共同好友、跨服务推荐添加 |
| 群管理 | 预置群号 1001~1006；加入群、退出群、挨踢、查询群成员；平台理念差异：QQ 群可申请加入而微信群只能推荐加入、QQ 群允许临时讨论组而微信群不允许、QQ 群有以群主为核心的管理员制度而微信群仅有群主为特权账号 | 全部实现，另实现聚合根体系的完整群管理（12 种操作） |
| 开通管理 | 用户可自选开通 N 个微 X 服务 | 全部实现，含开通资格校验与幂等 |
| 登录管理 | 各微 X 之间只要有一个服务登录，其它服务经简单确认视为自动登录 | 实现为一个服务登录后本人其余已开通服务自动上线 |
| 功能展示要求（main 函数） | ① 开通情况、群成员、好友信息预存文件并在启动时载入内存；② 一个服务登录后其余已开通服务进入开通状态；③ 可依据另一服务的好友关系添加好友；④ 展示某服务的群特色功能，并在群成员数据不受伤害的前提下动态变换为其它类型群的管理特色；⑤ QQ 点对点 TCP 通信（选做） | ①~④ 全部实现并有自动演示与断言；⑤ 选做项未实现 |

系统对外提供两种使用方式：一是 `--demo` 自动演示，按 A→D 四段依次跑完全部功能展示要求并输出自检汇总；二是手动测试工作台，按真实 IM 客户端的操作路径组织菜单，供逐项走查与答辩演示。

## 1.3 重点与难点分析

### 1.3.1 设计重点

1. **把平台差异收敛到可替换的少数规则上。** 群的核心流程（发消息、踢人、禁言、转让、解散）与平台无关，差异只集中在「谁能邀请」「谁能设置全员禁言」等少数规则；如果把这些判断写在业务方法里，代码会充满平台分支。
2. **用聚合根集中维护群的不变量。** 成员唯一、人数上限、任意时刻至多一个群主、解散后一切操作被拒绝——这些约束一旦分散，就很容易被绕过。
3. **多产品身份的统一建模。** 「自然人 + 多平台账号」的结构决定了好友、群成员、消息能力能否自然地按平台隔离。
4. **可验证性。** 课程设计要求逐条实现任务书条目，因此需要把「需求条目」变成可执行的断言，而不是靠人工核对。

### 1.3.2 主要难点

1. **如何判断哪些规则「相同」、哪些「不同」。** 微信群「仅群主为特权账号」与 QQ 群「管理员制度」的差异看似在权限判断里，实际只需在最后一步覆写；而「禁言期间不能发言」「不能撤回他人消息」这类约束两平台完全一致，必须上提共用，否则迟早出现两平台不一致。
2. **动态变换管理模式时数据不受伤害。** 任务书 6.(4) 要求在群成员数据不受伤害的前提下把群动态变为其它类型群的管理特色，这要求群的状态与授权策略彻底解耦。
3. **权限判断的三层结构。** 公共角色权限、公共状态约束、平台差异规则必须各归其位，任何一层写到错误的层里都会留下漏洞。
4. **断电保存的时机与格式。** 任务书要求「容器实例化时读入、析构时写回」，因此持久化不能侵入业务代码；同时自由文本（昵称、群名、消息、备注）中可能包含分隔符，需要最小转义。
5. **控制台界面的可读性与重绘正确性。** 全数字键的单键交互、每次操作后重绘、界面不能因窗口尺寸而出现内容被顶出屏幕的显示缺陷，都是需要专门处理的工程问题。

## 1.4 技术难点说明

1. **多态的边界划分。** 抽象太浅则子类重复实现公共逻辑，抽象太深则父类被迫知道具体平台。本设计的做法是把授权过程固定为六步模板方法，`isAllowed` 声明为 `final`，平台子类**只能覆写最后一步** `checkPlatformRule`，并规定「两平台一致的规则必须上提到父类」。
2. **对象生命周期与所有权表达。** 群持有成员与消息、成员关联用户、授权上下文引用群与操作者——若全部用 `shared_ptr` 会形成循环引用。本设计用「组合（`GroupConfigFH`）、聚合（`GroupMembershipFH`、`MessageFH`）、依赖抽象（`GroupPolicyFH`）、非拥有裸指针（`GroupContextFH` 指向群）」四种不同强度的关系分别表达。
3. **构造期的求值顺序陷阱。** 在 `members_.emplace(id, GroupMembershipFH(std::move(owner), OWNER))` 这类表达式中，实参求值顺序不确定：先取 ID 再 `std::move`，否则会出现解引用已移动对象的问题。本设计显式先取 ID 再移动，并在代码注释中记录原因。
4. **跨平台终端行为差异。** Windows 与 POSIX 的单键读取方式不同（前者用控制台 API，后者需临时切换终端到非规范模式）；输出侧要处理 UTF-8 编码与中文显示宽度（全角字符占两列），否则对齐与折行都会算错。
5. **中文与 UTF-8 的处理。** MSVC 需要 `/utf-8` 编译选项与 `SetConsoleOutputCP(CP_UTF8)`，否则中文注释与输出会乱码；界面排版还需要自行实现「按显示宽度」的截断、折行与补空格。

# 二、设计方案

## 2.1 功能模块划分

系统按职责分为六个模块，模块之间只通过公开接口协作，目录结构与模块划分一致。

### 2.2.3 对象关系说明

| 关系 | 双方 | 强度与理由 |
|---|---|---|
| 组合 | `GroupFH` *-- `GroupConfigFH` | 配置随群生灭，群销毁配置即无意义 |
| 聚合 | `GroupFH` o-- `GroupMembershipFH` / `MessageFH` | 成员与消息的生命周期受群管理，但可单独查询 |
| 关联 | `GroupMembershipFH` --> `UserFH`、--> `GroupRoleFH` | **角色属于「成员关系」而非「用户」**：同一用户在不同群可有不同角色 |
| 依赖抽象 | `GroupFH` --> `GroupPolicyFH` | 运行期可换绑具体策略（`switchPolicy`） |
| 非拥有引用 | `GroupContextFH` --> `GroupFH` | 授权上下文只在一次调用内存活，用裸指针避免循环引用 |
| 依赖 | 注册表 ..> `UserProfileFH` / `PlatformMessagePolicyFH` | 好友、群成员、消息能力统一落到「平台 × 账号」维度 |

### 2.2.4 关键设计决策

**决策一：用策略模式（Strategy）消除业务方法里的平台分支。** `GroupFH` 只依赖 `GroupPolicyFH` 抽象，构造时注入具体策略，类中不出现任何「平台等于 QQ 就怎样」的判断。新增一个微 X 产品，主要是新增一个策略实现，而不是修改群类。

**决策二：用模板方法（Template Method）固定公共授权流程。** 以继承明确表达「同类算法中可替换的步骤」：

```text
validateContext → checkMembership → checkPermission
→ checkTargetPermission → checkStateRules → checkPlatformRule（多态）
```

`isAllowed` 为 `final`，子类无法改变判断顺序；同时规定两平台一致的规则必须上提到父类（禁言、撤回归属与时间窗）。

**决策三：群作为聚合根集中维护不变量。** 成员容器以用户 ID 为键（天然去重、O(1) 查找）、人数上限、至多一个群主（构造时注入）、解散后一律拒绝——外部只能通过业务方法修改状态，拿不到成员容器的可写引用。

**决策四：角色挂在成员关系上。** 若角色挂在用户上，同一用户在不同群无法拥有不同角色，也与真实 IM 不符。

**决策五：多产品身份用「自然人档案 + 平台账号」建模。** `UserProfileFH` 表示自然人，`platformAccountId(platform)` 解析其在某平台的号码：QQ 与微博返回同一号码，微信返回独立号码并可用 `bindWeChat` 绑定一个 QQ 号。

**决策六：模式克制，不为演示而堆抽象。** 阶段 C/D 的平台差异一律收敛到集中规则类（好友差异在 `FriendRegistryFH`、群号与入群规则在 `GroupRegistryFH`、消息能力在 `PlatformMessagePolicyFH`），不引入规则引擎、插件系统或万能参数对象。

## 2.3 数据定义

### 2.3.1 为什么没有采用数据库

本设计是**单机内存模型**：没有网络服务、没有多进程并发访问，数据规模为个位数的自然人与几十条消息。在这种前提下引入数据库会显著增加构建依赖（课程环境要求离线可构建、无第三方依赖），而收益仅是形式上的「有数据库」。因此数据组织采用「内存容器 + 文件持久化」：运行时全部数据位于内存容器中，持久化只在容器构造（读入）与析构（写回）两个时机发生，等价实现了任务书要求的断电保存。

因此本节给出的是**实体字段定义**与**存档文件格式定义**，二者共同构成系统的数据定义。

### 2.3.2 实体字段定义

| 实体（类） | 关键字段 | 说明 |
|---|---|---|
| `UserFH` | `id`、`nickname` | 某一平台上的用户实体（群成员、消息发送者引用它） |
| `UserProfileFH` | QQ 号、微信 ID（可空）、微博号、昵称、出生日期、所在地、T 龄起算年、已开通平台集合、在线平台集合 | 自然人档案，跨平台身份的唯一入口 |
| `AccountInfoFH` | 平台、账号、昵称、绑定的 QQ 号 | 某平台账号视图（`makeAccount` 生成） |
| `GroupFH` | 群 ID、群号、群名、群配置（组合）、成员表（聚合）、消息列表（聚合）、公告、策略引用、是否解散 | 聚合根，群全部状态与不变量的持有者 |
| `GroupMembershipFH` | 用户（`shared_ptr`）、角色、是否被单员禁言、入群时刻 | 角色与禁言状态的宿主 |
| `GroupConfigFH` | 人数上限、普通成员邀请开关（QQ 概念）、全员禁言标志、撤回时间窗（秒） | 可变配置，变更即校验 |
| `MessageFH` | 消息 ID、发送者、内容、类型、发送时刻、是否已撤回 | 聚合根内部的消息实体（可注入发送时刻以便演示时间窗） |
| `FriendShipFH` | 平台、拥有者 ID、对方 ID、是否双向、备注 | 好友/关注边，备注的视角属于设置者 |
| `GroupInfoFH` | 平台、群号、群名、群主 ID、管理员 ID 集合、成员 ID 集合、容量、是否预置、聊天记录 | 群注册表体系的群信息载体 |
| `GroupChatRecordFH` | 类型、发送者 ID、发送者昵称、内容、是否引用、发送时刻 | 群聊记录（按平台视图渲染） |

### 2.3.3 存档文件格式

三个存档文件均为**行式文本**（`std::ios::binary` 打开以避免平台换行转换），每行一条记录，字段之间用 ASCII 单元分隔符 `0x1F` 分隔，因此不会与昵称、群名、消息内容里的常规字符冲突。自由文本字段做最小转义（反斜杠、换行、分隔符本身），由 `PersistUtilFH::escapeTextFH / unescapeTextFH` 负责。

| 文件 | 记录 | 格式（字段以 ␟ 表示 0x1F） |
|---|---|---|
| `save_activation_fh.dat` | `A` 开通记录 | `A ␟ QQ号 ␟ 平台名 ␟ 平台名 …`（平台名为 0~N 个已开通服务） |
| `save_friends_fh.dat` | `F` 好友边 | `F ␟ 平台 ␟ 拥有者ID ␟ 对方ID ␟ 是否双向(0/1) ␟ 备注(转义)` |
| `save_groups_fh.dat` | `G` 群信息 | `G ␟ 平台 ␟ 群号 ␟ 群名(转义) ␟ 群主ID ␟ 容量 ␟ 是否预置(0/1) ␟ 管理员ID列表(逗号分隔) ␟ 成员ID列表(逗号分隔)` |
| `save_groups_fh.dat` | `M` 群聊记录 | `M ␟ 群号 ␟ 类型(整型) ␟ 发送者ID ␟ 发送者昵称(转义) ␟ 内容(转义) ␟ 是否引用(0/1) ␟ 发送时刻(计数)` |

读写时机与容错：

- 三个容器各自提供 `setActivationPath` / `setPersistencePath`，**在构造函数中读入**、**在析构函数中写回**，业务代码不感知持久化；
- 读入时逐行解析并包在 `try/catch` 中，存档被截断或篡改不会导致启动崩溃；无法解析的记录行直接跳过；
- `A` 记录按 QQ 号与已注册档案匹配，未注册的档案跳过；加载完成后自建群号从「现有最大群号 + 1」继续分配，避免与预置群号冲突；
- 存档文件由程序在**运行目录**生成，已在 `.gitignore` 中按文件名模式排除。

## 2.4 UI 设计

### 2.4.1 交互路径与键位

界面按真实 IM 客户端的操作路径组织：选择自然人 → 账号中心（开通 / 登录）→ 官方群大厅（浏览与加入）或创建（建群 / 讨论组）→ 会话内操作；通讯录用于好友与关注管理。

- **键位约定**：全部操作项为数字键，`0` 统一为「返回上级 / 进入更多操作」，单键即触发、无需回车；账号选择、群大厅等列表型界面的功能键按列表长度**动态编号**，避免与列表项冲突。
- **反馈**：底部状态条显示每次操作的成功或失败原因，失败原因按规则链给出中文说明（如「微信群仅群主可设置全员禁言（平台差异）」「不能禁言与自己同级或更高等级成员」）。
- **防呆**：文本输入直接回车即取消；解散群需二次确认；无效按键给出提示；群主退群被拒时提示先转让或解散。
- **状态标注**：好友与成员选择列表在每项后标注当前关系（`［已是QQ好友］`、`［已关注］`、`［已在群内］` 等）。同一个选择器同时服务「加好友」与「删好友」等相反意图，因此采用标注而非过滤名单：既避免误操作，也保留「重复添加被拒绝」这类规则的可演示性。

### 2.4.2 界面排版规范

控制台界面由一个独立的排版模块统一负责（`app/ui_screen.hpp/.cpp`），全部界面遵循同一套规范：

- **结构**：标题栏 → 键值卡片 → `—— 小节 ——` → 对齐菜单 → 状态条 → 提示行；
- **对齐**：按**显示宽度**对齐（中文全角与中文环境下按全角渲染的标点按 2 列计），键值卡片与菜单列因此能整齐对齐；
- **尺寸约束**：输出行数受终端可视行数约束、每行宽度受可视列数约束，超出一屏的列表项折叠为「…… 还有 N 条」，长帮助页按可视高度自动分页。这条约束把「界面会不会把标题顶出屏幕」从随机现象变成了可测的不变量；
- **列表分行**：列表型界面（账号、群、候选成员）保持一行一个，操作菜单按终端宽度自适应列数。

### 2.4.3 自动演示

`--demo` 按 A→D 四段依次演示：A 核心流程（QQ 群 vs 微信群）、B 多产品账号与登录联动、C 好友与群注册表、D 群消息平台差异。演示结束输出自检汇总，给出校验项总数、其中「应失败」项数与是否符合预期；`--demo=A|B|C|D` 可只演示其中一段，便于答辩时按需切换。

## 2.5 设计模式的使用

| 模式 | 落点 | 解决的问题 |
|---|---|---|
| 策略模式 Strategy | `GroupPolicyFH` 接口 + `QQPolicyFH` / `WeChatPolicyFH` | 把平台差异从群业务方法中移出，使其可独立替换 |
| 模板方法 Template Method | `AbstractGroupPolicyFH::isAllowed`（`final`）+ 子类覆写 `checkPlatformRule` | 固定公共授权流程，避免子类复制粘贴与漏判 |
| 聚合根 Aggregate | `GroupFH` | 集中维护群不变量，外部无法绕过 |
| 组合优于继承 | 角色挂在 `GroupMembershipFH` 上 | 同一用户在不同群拥有不同角色 |

同时刻意**没有**引入的设计：

- 不为好友、群、消息各造一套抽象工厂或访问者：这三类结构的差异是数据差异，用集中规则类即可表达；
- 不引入责任链处理授权：授权步骤是固定的六步且顺序有意义，链式装配反而会掩盖顺序约束；
- 不引入插件式动态加载：当前只需在编译期支持多平台，接口已预留扩展点，但不必提前引入运行时装配的复杂度。

## 2.6 权限模型与核心调用链

权限判断分三层：公共角色权限 → 公共状态约束 → 平台差异规则。

| 操作（Action） | 群主 | 管理员 | 普通成员 | QQ 差异 | 微信差异 |
|---|---|---|---|---|---|
| 发送消息 | 允许 | 允许 | 允许 | — | — |
| 撤回消息 | 允许 | 允许 | 仅本人 | — | — |
| 邀请成员 | 允许 | 允许 | 见差异 | 成员邀请开关开启时允许 | 禁止（仅群主可推荐） |
| 踢出成员 | 允许 | 允许 | 禁止 | — | — |
| 禁言成员 | 允许 | 允许 | 禁止 | — | — |
| 修改群资料 / 发公告 | 允许 | 允许 | 禁止 | — | — |
| 全员禁言 | 允许 | 允许 | 禁止 | 管理员及以上可设 | 仅群主可设 |
| 任命管理员 / 转让群主 / 解散群 | 允许 | 禁止 | 禁止 | — | — |

补充规则：踢人与禁言**不能作用于同级或更高角色**；撤回受时间窗约束且不可重复撤回；被单员禁言或全员禁言期间普通成员不能发言，管理员与群主不受影响。

核心调用链以「发送消息」为例：

```text
控制台工作台
   └─ GroupFH::sendMessage(操作者, 消息)
        ├─ 校验消息发送者与操作者一致
        ├─ 组装 GroupContextFH（群、操作者、消息、当前时刻）
        ├─ GroupPolicyFH::isAllowed(SEND_MESSAGE, ctx)
        │     └─ AbstractGroupPolicyFH::isAllowed（final，六步）
        │          1 上下文合法 → 2 成员关系 → 3 公共角色权限
        │          → 4 目标权限 → 5 状态约束（禁言 / 全员禁言）
        │          → 6 checkPlatformRule（多态，平台差异）
        └─ 授权通过则追加消息；否则拒绝并由界面给出中文原因
```

## 3.2 核心流程

**流程一：群操作授权（所有群操作的统一入口）。** 业务方法先组装上下文，再交给策略判断，通过后才修改状态；授权失败不产生任何状态变更。

```text
setAdmin(操作者, 目标, true)
  → 组装 GroupContextFH（注入当前时刻）
  → isAllowed(ASSIGN_ADMIN, ctx)：六步判断，含平台差异
  → true：修改成员角色；false：返回失败（界面显示中文原因）
```

**流程二：群消息发送（阶段 D 的平台差异）。** 群注册表侧的发送流程先做「群存在且平台匹配」「发送者是群成员」两项检查，再委托 `PlatformMessagePolicyFH` 校验消息类型、文本长度与引用能力，全部通过后追加群聊记录，超过 50 条上限时淘汰最旧记录。

**流程三：开通与登录联动（任务书 4、5、6.(2)）。** 开通时校验资格（例如开通微信前必须先绑定微信号），重复开通按幂等处理；取消开通要求该服务已离线。登录时要求服务已开通，登录成功后本人**其余已开通服务自动上线**，退出登录则只影响单个服务。

**流程四：容器加载与写回（断电保存）。** 容器构造时若配置了存档路径则读入文件并重建内存状态；程序退出时容器析构，自动把内存状态写回文件。演示 [C6] 用一个作用域模拟「进程一写回 → 进程二重启加载」，验证往返一致。

## 3.3 核心方法与关键代码

**（1）六步授权链（模板方法）。** `isAllowed` 声明为 `final`，固定判断顺序：

```cpp
bool AbstractGroupPolicyFH::isAllowed(ActionFH action, const GroupContextFH& c) const {
    return validateContext(action, c)          // 1 上下文合法
        && checkMembership(action, c)          // 2 成员关系（邀请时目标须不在群内）
        && checkPermission(action, c)          // 3 公共角色权限
        && checkTargetPermission(action, c)    // 4 目标权限（不能操作同级 / 更高级）
        && checkStateRules(action, c)          // 5 公共状态约束
        && checkPlatformRule(action, c);       // 6 平台差异（多态）
}
```

**（2）公共状态约束上提父类。** 禁言与撤回的约束两平台完全一致，放在第 5 步统一实现；此前它们曾在两个子类中重复实现，重构后消除了不一致隐患：

```cpp
case ActionFH::SEND_MESSAGE:
    if (c.group->isMuted(c.operatorUser) && !isPrivileged(c)) return false;  // 单员禁言
    return isPrivileged(c) || !cfg.isAllMuted();                             // 全员禁言
case ActionFH::RECALL_MESSAGE:
    if (!c.message || c.message->isRecalled()) return false;                 // 不可重复撤回
    if (!isPrivileged(c) && 发送者 != 操作者) return false;                    // 普通成员限本人
    return c.now <= c.message->getSentAt() + cfg.getRecallTimeLimit();       // 时间窗
```

**（3）平台差异只留一个覆写点。** 两个子类只保留真正存在差异的规则：

```cpp
// QQ：普通成员邀请由配置开关控制；管理员及以上可设全员禁言
case ActionFH::INVITE_MEMBER: return cfg.isMemberInviteEnabled() || isPrivileged(c);
case ActionFH::SET_ALL_MUTE:  return isPrivileged(c);

// 微信：仅群主可推荐加入、仅群主可设全员禁言（任务书 3.(3)）
case ActionFH::INVITE_MEMBER: return c.group->getRole(c.operatorUser) == GroupRoleFH::OWNER;
case ActionFH::SET_ALL_MUTE:  return c.group->getRole(c.operatorUser) == GroupRoleFH::OWNER;
```

**（4）聚合根构造时注入群主，保证至多一个群主。**

```cpp
GroupFH::GroupFH(std::string id, unsigned groupNumber, std::string name,
                 GroupConfigFH config, std::shared_ptr<GroupPolicyFH> policy,
                 std::shared_ptr<UserFH> owner) {
    config_.validate();
    if (id_.empty() || name_.empty()) throw std::invalid_argument("...");
    if (!policy_) throw std::invalid_argument("GroupFH: policy is required");
    if (!owner || owner->getId().empty()) throw std::invalid_argument("GroupFH: owner is required");
    // 注意：先取 ID 再 std::move —— emplace 实参求值顺序不确定
    const std::string ownerId = owner->getId();
    members_.emplace(ownerId, GroupMembershipFH(std::move(owner), GroupRoleFH::OWNER));
}
```

**（5）转让群主时原子交换角色，避免「无主」或「双主」的中间状态。**

```cpp
if (!execute(ActionFH::TRANSFER_OWNER, c)) return false;
membershipOf(op).setRole(GroupRoleFH::MEMBER);     // 原群主降级
membershipOf(target).setRole(GroupRoleFH::OWNER);  // 新群主升级
```

**（6）主动退群由聚合根兜底维护「群不能无主」。**

```cpp
bool GroupFH::leaveGroup(const std::shared_ptr<UserFH>& op) {
    if (disbanded_ || !op) return false;
    const auto role = getRole(op);
    if (!role || *role == GroupRoleFH::OWNER) return false;  // 群主须先转让或解散
    return members_.erase(idOf(op)) == 1;
}
```

**（7）动态变换管理模式只换策略对象。**

```cpp
bool GroupFH::switchPolicy(const std::shared_ptr<GroupPolicyFH>& newPolicy) noexcept {
    if (disbanded_ || !newPolicy) return false;
    policy_ = newPolicy;   // 仅换策略，成员 / 消息 / 配置数据不受伤害
    return true;
}
```

## 3.4 核心功能实现

**（1）领域实体与聚合根。** 角色用 `enum class GroupRoleFH { MEMBER = 1, ADMIN = 2, OWNER = 3 }` 表达（枚举值有序，因此「不能操作同级或更高角色」可以直接比较）；群配置集中在 `GroupConfigFH` 且变更即校验；群的全部状态由 `GroupFH` 持有，对外只暴露业务方法。`GroupFH` 的 12 种操作与 2 种配置变更全部遵循「构造上下文 → 策略授权 → 通过才改状态」的模式。

| 业务方法 | 说明 |
|---|---|
| `sendMessage` / `recallMessage` | 发消息（发送者须为本人）/ 撤回（归属 + 时间窗） |
| `inviteMember` / `kickMember` / `leaveGroup` | 邀请 / 踢出 / 主动退群（群主不可直接退群） |
| `muteMember` / `setAllMute` | 单员禁言 / 全员禁言 |
| `editGroup` / `publishAnnouncement` | 改群名 / 发公告 |
| `setAdmin` / `transferOwner` / `disband` | 任免管理员 / 转让群主 / 解散 |
| `setRecallTimeLimit` / `setMemberInviteEnabled` | 群配置运行期变更（走修改群资料授权） |
| `switchPolicy` | 动态切换管理模式 |

**（2）多产品体系（任务书 1、4、5）。** 号码体系由 `UserProfileFH` 与 `AccountInfoFH` 承担：QQ 与微博返回同一号码，微信为独立号码并可绑定一个 QQ 号。`ActivationManagerFH` 负责自选开通（资格校验 + 幂等 + 在线不可取消），`LoginManagerFH` 负责登录联动。自然人同时持有「已开通集合」与「在线集合」，界面账号卡片实时展示三项服务的「未开通 / 已开通 / 在线」状态。

**（3）社交关系（任务书 2、3）。** 好友按平台隔离：QQ 与微信为双向好友，微博为单向关注（关注 ≠ 好友，`isFriend` 与 `isFollowing` 语义分离）；删除 QQ 好友不影响微信好友关系。备注的视角属于设置者。共同好友通过好友边交集计算（微博侧为共同关注）。跨服务推荐添加先做四项资格校验（本人已开通来源与目标服务、对方已是来源服务好友且已绑定目标服务、且尚非目标服务好友），再完成添加。群注册表预置 1001~1006，自建群从 1007 起自动续编；QQ 与微博群可申请加入，微信群直接申请被拒、须由群内成员推荐；QQ 临时讨论组容量 20、任何成员可邀请、成员自由退、仅发起人可解散。

**（4）消息平台差异（自定扩展）。**

| 能力 | QQ 群 | 微信群 | 微博群 |
|---|---|---|---|
| 消息类型 | 全部支持 | 禁文件（课程简化） | 仅文本 / 表情（课程简化） |
| 文本长度上限 | 8000 | 5000 | 1000 |
| 引用回复 | 支持 | 支持 | 不支持 |

消息实体携带类型枚举，发送前由 `PlatformMessagePolicyFH` 统一校验类型、长度与引用能力；群聊记录上限 50 条并自动淘汰最早记录。同一份内容在不同平台的渲染形态不同（产品视图差异），由该策略类的 `render` 方法统一给出。

**（5）断电保存（任务书 6.(1)、优化(2)）。** 三个容器统一提供 `setPersistencePath` 风格接口，构造时读入、析构时写回；行式文本 + `0x1F` 分隔 + 自由文本最小转义；解析包在 `try/catch` 中，坏行跳过而不崩溃。工作台启动时从存档恢复并在状态条告知，退出时写回。

**（6）交互界面与终端排版。** 工作台的全部界面由一个排版模块统一绘制：整帧先缓冲，再按终端可视尺寸裁剪后重绘（回到首行逐行覆盖，末行不发送换行符，因此光标始终停在可视区内）。超屏时先丢空行、再丢列表项、最后才丢正文，标题、菜单、状态条与提示行永不裁剪。中文按显示宽度对齐（全角与中文环境下按全角渲染的标点按 2 列计），键值卡片与菜单列因此能整齐对齐。

**（7）自动演示与自检。** `--demo` 四段共 66 项校验，每项用 `ok()` / `okDenied()` 包装：前者期望成功，后者期望被平台规则或权限拒绝（即「应失败」）。演示结束输出「校验项总数 / 成功数 / 应失败数 / 是否符合预期」，任何一处与预期不符都会在汇总中被标红列出，取代了人工逐行核对。

## 3.5 相关技术讨论

### 3.5.1 持久层的使用

- **职责边界**：持久化能力由容器自身提供（构造读入、析构写回），业务代码不感知；群聚合根等纯领域对象不承担 I/O。
- **格式选择**：行式文本而非 JSON。行式文本便于「逐行解析 + 坏行跳过」，无需引入第三方解析库，且便于人工查看与手工构造测试数据。
- **分隔符选择**：用 ASCII 单元分隔符 `0x1F` 而不是逗号、制表符，避免与昵称、群名、消息内容里的常规字符冲突；对自由文本再做最小转义（反斜杠、换行、分隔符）。
- **容错**：读入时逐行 `try/catch`，字段数不足或平台名非法的记录直接跳过；加载完成后自建群号从已有最大群号 + 1 续编，避免与预置群号冲突。
- **落地效果**：`--demo` 中的 [C6] 段用「进程一写回 → 进程二重启加载」验证往返一致，属于任务书 6.(1) 的可演示证据。

### 3.5.2 多线程

本设计**有意保持单线程**：系统是单机内存模型，所有业务操作都是内存中的同步调用，不存在共享状态的并发访问；引入线程只会带来加锁与竞态的额外复杂度，不产生实际收益。

工程中唯一的线程相关代码是工作台的「操作处理中」反馈动画（`busy()`），它用 `std::this_thread::sleep_for` 在极短时间内展示处理过程；该动画默认关闭（每次操作固定延迟约 225 ms 会让操作明显变慢），需要讲解时用 `FH_UI_ANIM=1` 开启。此外，单键输入在 POSIX 下依靠终端属性切换实现，不涉及线程。

如果后续接入真实网络服务，需要引入的将是「IO 多路复用 + 工作线程池」，而不是简单地给现有调用加锁；届时群聚合根需要改为「单群单线程串行处理」以继续保证不变量。

### 3.5.3 容器的使用

| 容器 | 使用位置 | 选择理由 |
|---|---|---|
| `std::unordered_map` | 群成员表（键为用户 ID）、平台账号池、注册表索引 | 成员唯一性由键天然保证，插入 / 查找平均 O(1) |
| `std::vector` | 消息列表、群列表、好友 ID 列表、候选列表 | 需要保持插入顺序（消息按时间、群按创建顺序），且以顺序遍历为主 |
| `std::set` | 在线平台集合、已开通平台集合 | 需要去重且有序（界面按平台顺序展示） |
| `std::shared_ptr` | 用户、群、策略对象的共享所有权 | 用户被多个群或多个注册表引用，需共享生命周期 |
| `std::weak_ptr` | 群成员表中对用户的引用场景（避免循环引用） | 与 `shared_ptr` 配合表达非拥有关系 |
| 裸指针（非拥有） | `GroupContextFH` 指向群 | 上下文只在一次授权调用内有效，用裸指针表达「不参与所有权」 |
| `std::optional` | 平台选择、文本输入等「可能无值」的返回值 | 比用空串或 `-1` 表达「取消」更明确 |
| `std::function` | 选择器的标注回调（当前关系标注） | 同一选择器复用于加/删好友等相反意图 |

容器的封装原则：成员容器不对业务层暴露可写引用（只能通过 `GroupFH` 的业务方法修改），对外只提供 `const` 只读访问，从而保证不变量不被绕过。

### 3.5.4 字符串与中文编码

源码与运行期字符串统一 UTF-8：MSVC 增加 `/utf-8`，控制台切换输出代码页；界面的截断、折行、补空格全部按**显示宽度**计算（全角字符 2 列、ASCII 1 列、组合符号 0 列），并对中文环境下按全角渲染的标点（破折号、间隔号、引号、箭头等）按 2 列高估——高估只会让折行略早，不会让行超出终端。群聊记录的存储同样保持 UTF-8，转义只处理控制字符与分隔符，不改变编码。

### 3.5.5 跨平台处理

| 差异点 | Windows | POSIX（macOS / Linux） |
|---|---|---|
| 单键读取 | `_getch()`（功能键前缀吞掉第二字节） | 临时清除 `ICANON` / `ECHO`（保留 `ISIG`，Ctrl+C 仍有效）后逐字节读 |
| 屏幕重绘 | 打开虚拟终端序列处理；老终端回退控制台 API | ANSI 序列 |
| 控制台尺寸 | 控制台窗口信息（可视窗口而非缓冲区） | `ioctl(TIOCGWINSZ)` |
| 中文输出 | 设置输出代码页为 UTF-8 | 终端本身为 UTF-8 |
| 非交互环境 | 检测到非控制台句柄时回退标准输入逐字节读取 | 非终端时不做任何属性切换 |

三平台共用同一套业务代码，差异全部集中在表现层的少量适配代码中；输入流结束时程序直接退出，因此重定向运行（如把演示输出写入文件）也能正常结束。

# 四、总结与体会

## 4.1 难点问题讨论与解决方案

调试过程中出现并解决的主要问题如下。

| # | 问题 | 解决方案 |
|---|---|---|
| 1 | 全员禁言判断在两个平台策略中重复实现，且成员关系中的禁言标志从未被消费，导致**单员禁言实际失效** | 新增公共步骤「状态约束」，把两平台一致的禁言与撤回约束上提到父类，子类删除重复逻辑，单员禁言随之生效 |
| 2 | 微信邀请规则口径矛盾：设计文档写「管理员以上」，代码用「是否为管理员及以上」，而任务书 3.(3) 是「微信群仅有群主为特权账号」 | 以任务书为准统一为仅群主可邀请、仅群主可设全员禁言，同步修改策略实现、测试用例与演示文案 |
| 3 | 撤回时间窗（120 秒）在手动测试中无法触发超时分支 | 利用消息实体可注入发送时刻的构造参数，在演示中构造「121 秒前发送」的消息复现超时；界面同时开放撤回窗口配置，可现场调小验证 |
| 4 | 切换管理模式后，操作者身份仍按原平台账号计算，微信模式下仍用 QQ 账号操作 | 会话主循环每轮重算操作者；若当前自然人在新模式平台无账号，则降级为只读浏览并给出提示 |
| 5 | 群主可直接退群会导致群处于「无主」状态 | 退群方法中拒绝群主退群，提示「请先转让群主或解散群」，并补充对应测试用例 |
| 6 | MSVC 下中文注释与输出乱码 | CMake 中为 MSVC 增加 `/utf-8`，程序入口设置控制台输出代码页为 UTF-8 |
| 7 | 群构造函数中 `emplace` 实参求值顺序不确定，先移动再取 ID 会解引用已移动对象 | 先取出 ID 再 `std::move`，并在代码注释中记录原因 |
| 8 | 演示写回的存档文件污染工作区并被误纳入版本库 | 按文件名模式加入 `.gitignore`，演示结束用删除接口清理临时文件 |
| 9 | 加载存档后自建群号可能与预置群号冲突 | 加载后自建群号从「现有最大群号 + 1」继续分配 |
| 10 | 控制台单键读取在管道 / 重定向环境（自动化冒烟）下取不到控制台句柄 | 检测控制台句柄失败后回退为标准输入逐字节读取，保证非交互环境仍可运行 |
| 11 | 文档与实现漂移（文档中的套件数量、重启是否保留数据等表述与代码不符） | 建立「改动后同步文档」的习惯，按代码实际状态逐项校正各文档 |
| 12 | 工作台在 macOS / Linux 下按数字键没有反应，必须再按一次回车（Windows 下正常） | 根因是 POSIX 终端默认处于规范模式，需等到回车才把字节交给程序。新增终端属性守卫：读取单键时临时清除规范模式与回显（保留信号处理，Ctrl+C 仍有效），读完立即恢复；非终端环境不做改动 |

其中最具代表性的一次排查是**界面「每按一次键就多跳一段」的显示缺陷**：现象是标题栏与首行信息被顶出屏幕，且时好时坏。排查后确认根因并非渲染逻辑写错，而是**输出量没有与终端尺寸对齐**——每帧清屏后逐行直接输出，从不查询终端可视高度，帧行数一旦超过窗口高度，写入越过底行就会让控制台向上滚动；而溢出通常只有一两行（多打印的空行、状态条与提示行的固定开销、帧后追加的行内子提示），所以表现为「有时正常、有时缺一行」。修复方案是把重绘改为「整帧缓冲 + 按终端可视尺寸裁剪 + 回首行逐行覆盖」，并把「输出行数不超过可视行数、每行宽度不超过可视列数」写成可断言的不变量；修复后在不同窗口高度（含 simulate 的矮窗口）下都能完整显示。这次经历说明：**偶发的显示问题应当先怀疑「有没有把环境约束写进代码」，而不是渲染代码本身。**

## 4.2 程序设计的优点

1. **平台差异被多态消化。** 群聚合根中没有任何平台分支，新增产品主要是新增策略类，符合开闭原则，也便于在答辩中解释「为什么这样设计」。
2. **公共流程不会漏判。** 模板方法把两平台一致的规则固定在父类，从机制上避免了子类复制粘贴导致的规则遗漏。
3. **不变量集中维护。** 成员唯一、人数上限、单群主、解散后拒绝操作等由聚合根统一维护，业务方法外部无法绕过。
4. **角色归属正确。** 角色挂在成员关系上，转让群主只是一次角色交换，不需要搬运用户数据。
5. **多产品身份统一建模。** 「自然人 → 多平台账号」的结构使好友、群成员、消息能力天然按平台隔离，差异表达自然。
6. **模式克制。** 没有为了展示设计模式而制造抽象，规则集中在少数几个类里，可读性与可解释性较好。
7. **可验证性强。** 98 个用例覆盖任务书逐条要求，另有 66 项演示自检与手动工作台支持全流程走查；界面输出还建立了可测的尺寸不变量。

## 4.3 不足与限制

1. **单机内存模型**：无网络通信、无数据库、无真实平台接口，两个账号「同时在线」是同一进程内的模拟。
2. **任务书 6.(5) 的 QQ 点对点 TCP 通信未实现**（选做项）。
3. **规则为课程简化口径**：消息类型能力、文本长度上限、撤回时间窗等均为简化设定，不代表真实产品规则。
4. **断电保存覆盖三类数据**：开通情况、好友、群注册表；为演示聚合根而创建的本地正式群仅存在于当前进程。
5. **界面为控制台实现**：未做可视化（课程设计后作业方向，不考核）。
6. **单线程**：未考虑并发与加锁，若接入真实网络服务需要重新设计并发模型。

## 4.4 收获与展望

本次课程设计的主要体会有三点：

1. **面向对象首先是「职责划分」，其次才是语法特性。** 真正让代码变清晰的是把「群的状态」「授权流程」「平台差异」三件事分开，而不是把所有类都继承自同一个基类。
2. **「相同」比「不同」更值得抽象。** 平台差异只占少数规则，若把判断整体下放，重复的公共逻辑迟早会不一致；用模板方法把公共流程固定下来、差异只留一个覆写点，是本次设计中收益最大的决定。
3. **文档、测试与实现必须同步。** 本次出现的多处「规则与文案矛盾」都是三者不同步造成的；把任务书条目做成可执行的断言后，改动引起回归会立刻暴露。

后续可继续推进的方向：

- **选做的网络通信**：在现有平台账号与消息模型之上补齐 QQ 点对点 TCP 收发，验证消息层与网络层的解耦程度；
- **并发模型**：若接入真实服务，把群聚合根改为「单群串行处理」，用消息队列替代直接调用，保持不变量不被并发破坏；
- **持久化升级**：把行式文本存档升级为结构化格式（如二进制或 JSON），降低手工校对成本，并支持本地正式群落盘；
- **可视化界面**：在课程设计后作业的方向上，把控制台的交互层替换为图形界面，验证「表现层可替换」这一设计目标是否成立；
- **可扩展性验证**：按扩展点新增一个「微 X 产品」（例如微商），统计需要改动的文件数量，量化开闭原则的落实程度。
