## 一、设计任务分析

### 1.1 题目与背景

本课程设计的题目是「模拟即时通信系统实现」：某公司的即时通信业务先后推出 QQ、微信、微博等微 X 产品，各产品既可独立提供服务，又互相辉映关联，要求把它们整合为一个统一的立体社交软件平台，并完成设计、实现与验证。

本设计要解决的核心问题是：**当多个产品的业务「大部分相同、少部分不同」时，如何用面向对象的方法组织代码，使相同部分只写一遍、不同部分可以独立替换、新增产品时不必修改已有业务代码。** 好友关系要按平台隔离、群管理规则因平台而异、开通与登录要在多产品之间联动，因此这一问题是设计的出发点，也是衡量实现质量的主要标准。

### 1.2 系统功能描述

依据任务书，系统需要实现的功能可归纳为六类，如表 1 所示。

| 需求项 | 具体要求 |
|---|---|
| 用户基本信息 | 号码 ID、昵称、出生时间、T 龄、所在地、好友列表与群列表；QQ 与微博共享 ID，微信独立并可绑定 QQ 号 |
| 好友管理 | 好友的增、改、删、查；查询各微 X 之间的共同好友，并可依据另一服务的好友关系推荐添加 |
| 群管理 | 预置群号 1001~1006；加入群、退出群、挨踢、查询群成员；平台理念差异：QQ 群可申请加入而微信群只能推荐加入，QQ 群有临时讨论组而微信群没有，QQ 群有管理员制度而微信群仅群主为特权账号 |
| 开通管理 | 用户可以自选开通该平台的 N 个微 X 服务 |
| 登录管理 | 各微 X 之间只要有一个服务登录，其它服务经简单确认后视为自动登录 |

### 1.3 重点与难点分析

本设计的重点有三个。其一是**把平台差异收敛到少数可替换的规则上**：群的核心流程（发消息、踢人、禁言、转让、解散）与平台无关，差异只集中在「谁能邀请成员」「谁能设置全员禁言」等少数判断上。其二是**用聚合根集中维护群的不变量**：成员唯一、人数上限、任意时刻至多一个群主、解散后拒绝一切操作。其三是**多产品身份的统一建模**：「自然人 + 多平台账号」的结构决定了好友、群成员与消息能力能否按平台隔离。难点在于判断哪些规则「相同」、哪些「不同」：一致的约束（如禁言期间不能发言、不能撤回他人消息）必须上提到公共授权流程，否则迟早出现两平台不一致；而群的管理模式又要能动态变换，这要求群的状态与授权策略彻底解耦。

### 1.4 技术难点说明

技术难点集中在四处。一是**多态的边界划分**：抽象太浅则子类重复实现公共逻辑，太深则父类被迫知道具体平台，因此把授权过程固定为六步、只留最后一步多态。二是**对象所有权表达**：群持有成员与消息、成员关联用户、授权上下文引用群，若全部使用共享智能指针会形成循环引用，因此按关系强度分别使用组合、聚合、依赖抽象与非拥有裸指针。三是**构造期的求值顺序陷阱**：在成员表的插入表达式中先移动参数再取用户 ID 会解引用已移动对象，因此显式先取 ID 再移动。四是**跨平台与中文编码**：单键读取、屏幕重绘与控制台尺寸获取在两平台方式不同，中文还要按显示宽度计算全角字符占位，否则对齐与折行都会算错。

## 二、设计方案

### 2.1 功能模块划分

系统按职责分为领域模型、授权上下文与策略、多产品身份、社交关系、消息扩展、表现层六个模块，模块之间只通过公开接口协作，目录结构与模块划分一一对应：领域模型承载群与用户的实体，策略模块承载授权上下文、策略接口与公共授权流程，多产品身份模块承载自然人档案与平台账号，社交关系模块承载好友与群注册表，消息扩展模块承载消息类型与平台消息能力，表现层由工作台、自动演示与终端排版模块组成。模块的划分依据是「变化的原因」——领域实体因业务规则变化、策略类因平台差异变化、注册表类因数据组织方式变化，因此任一方面的改动都局限在该模块内部。

系统的核心骨架是一条「聚合根 + 策略」的结构，其类图如图 1 所示。

对象之间的关系按强度分别表达：GroupFH **组合** GroupConfigFH、**聚合** GroupMembershipFH 与 MessageFH；GroupMembershipFH **关联** UserFH 与 GroupRoleFH；GroupFH **依赖抽象** GroupPolicyFH，运行期可由 switchPolicy 换绑具体策略；GroupContextFH 对群使用**非拥有裸指针**，避免循环引用；各注册表类**依赖** UserProfileFH，把好友、群成员与消息能力统一落到「平台 × 账号」维度。

### 2.3 数据定义

本设计是**单机内存模型**：没有网络服务与并发访问，数据规模为个位数的自然人与几十条消息，引入数据库只会增加构建依赖而收益有限，因此采用「内存容器 + 文件持久化」——运行时数据全部位于内存容器，持久化只发生在容器构造（读入）与析构（写回）两个时机，等价实现了断电保存。需要落盘的字段包括：自然人的号码、昵称、出生日期、所在地、T 龄起算年、已开通与在线平台集合；平台账号与绑定关系；好友边的平台、双方、是否双向与备注；群的平台、群号、群名、群主、容量、管理员与成员；以及群聊记录的类型、发送者、内容与发送时刻。存档为行式文本，每行一条记录，字段之间以 ASCII 单元分隔符分隔并对自由文本做最小转义，因此不会与正文中的常规字符冲突。

### 2.4 权限模型与核心调用链

权限判断分为三层：公共角色权限、公共状态约束、平台差异规则，其中角色维度的规则如表 2 所示。

| 操作 | 群主 | 管理员 | 普通成员 | 平台差异（QQ / 微信） |
|---|---|---|---|---|
| 发送消息 | 允许 | 允许 | 允许 | 无 |
| 撤回消息 | 允许 | 允许 | 仅本人 | 受时间窗限制，不可重复撤回 |
| 邀请成员 | 允许 | 允许 | 见平台差异 | QQ 看成员邀请开关；微信仅群主 |
| 踢出、禁言成员 | 允许 | 允许 | 禁止 | 不能作用于同级或更高角色 |
| 设置全员禁言 | 允许 | 允许 | 禁止 | QQ 管理员及以上；微信仅群主 |
| 任免管理员、转让群主、解散群 | 允许 | 禁止 | 禁止 | 微信群无管理员，仅群主可执行 |

**表 2 权限模型**

全员禁言期间普通成员不能发言，管理员与群主不受影响。表中「微信仅群主」直接来自任务书 3.(3)：微信群中管理员角色不产生任何特权；把群从 QQ 模式切换为微信模式时，成员与角色数据原样保留，只是权限按当前策略重新解释。以发送消息为例，核心调用链为：业务方法先校验消息发送者与操作者一致，再组装包含群、操作者、消息与当前时刻的授权上下文并交由策略判断，判断依次经过上下文合法性、成员关系、公共角色权限、目标权限、公共状态约束与平台差异六步，通过后才追加消息，否则拒绝并由界面给出中文原因。

### 2.5 设计模式的使用

系统使用了三种设计模式。**策略模式**：群依赖策略接口而非具体平台，把平台差异从业务方法中移出，使其可独立替换。**模板方法**：公共授权流程固定在抽象基类中，六步顺序不可更改，子类只覆写平台差异一步，从机制上保证两平台一致的规则不会被漏判或复制。**聚合根**：群集中维护成员唯一、人数上限、至多一个群主、解散后拒绝操作等不变量，外部无法绕过。此外采用「组合优于继承」把角色挂在成员关系上，使同一用户在不同群可以拥有不同角色。刻意没有引入的设计有：不为好友、群、消息各造抽象工厂或访问者（它们的差异是数据差异，用集中规则类即可表达），以及不引入责任链处理授权（授权步骤固定且顺序有意义，链式装配反而掩盖顺序约束）。

## 三、详细设计

### 3.1 编译环境与构建

语言标准为 C++17（禁用编译器扩展）；主开发环境为 Windows 11 + Visual Studio 2022（MSVC v143）+ CMake，交叉验证环境为 Linux（GCC 13.3）与 MinGW g++ 15.2，三套环境共用同一份源码。第三方依赖为零，测试使用工程内自带的轻量断言框架，保证离线环境也能构建。MSVC 下增加 /utf-8 编译选项，程序入口把控制台输出代码页切换为 UTF-8，避免中文注释与输出乱码。规模上，头文件 27 个、实现文件 7 个、测试文件 9 个，合计约 8 400 行；构建流程为 CMake 配置与构建、CTest 运行回归测试，演示程序可进入手动工作台或执行自动演示。

### 3.2 核心流程

**群操作授权**：所有群操作统一为「组装上下文、策略授权、通过才改状态」，授权失败不产生任何状态变更。**群消息发送**：先校验群存在且平台匹配、发送者是群成员，再校验消息类型、长度与引用能力，全部通过后追加群聊记录，超过条数上限时自动淘汰最早记录。**开通与登录联动**：开通时校验资格（例如开通微信前须先绑定微信号），重复开通按幂等处理，取消开通要求该服务已离线；登录要求服务已开通，成功后本人其余已开通服务自动上线，退出登录只影响单个服务。**容器加载与写回**：容器构造时读入存档并重建内存状态，程序退出时容器析构自动写回，自动演示中还包含「进程一写回、进程二重启加载」的往返验证。

### 3.3 核心方法与核心功能实现

群聚合根对外只暴露业务方法，每个方法都遵循「先校验前置条件、再策略授权、通过后才修改状态」的同一模式，核心方法的实现要点如表 3 所示。

| 核心方法 | 实现要点 |
|---|---|
| sendMessage / recallMessage | 发送者须为本人；撤回受归属、时间窗与「不可重复撤回」约束 |
| inviteMember / kickMember | 邀请须过平台规则且目标不在群内；踢出要求管理员及以上且目标角色更低 |
| leaveGroup | 群主不能直接退群，须先转让群主或解散群，避免群处于无主状态 |
| muteMember / setAllMute | 单员禁言与全员禁言统一在公共状态约束中检查；设置权限见平台差异 |
| editGroup / publishAnnouncement | 修改群名与发布公告需要管理员及以上权限 |
| setAdmin / transferOwner / disband | 任免管理员、转让群主与解散群仅群主可执行；转让时原子交换角色 |
| switchPolicy 与群配置变更 | 切换管理模式只换绑策略对象，成员、消息与配置数据原样保留 |

**表 3 核心方法实现要点**

多产品身份由自然人档案与账号信息承担：QQ 与微博共用一个号码，微信使用独立号码并可绑定一个 QQ 号。社交关系按平台隔离：QQ 与微信是双向好友，微博是单向关注，关注不等于好友，删除某一平台的好友不影响另一平台的关系，备注的视角属于设置者本人；共同好友通过好友关系求交集得到，跨服务推荐添加则先校验双方均已开通对应服务、对方已是来源服务好友且已绑定目标服务、且尚不是目标服务好友。群注册表预置官方群 1001~1006，自建群自 1007 起自动续编，QQ 与微博群可申请加入、微信群须由群内成员推荐，QQ 群还可建立容量较小的临时讨论组。消息能力集中在一处规则类：QQ 群支持全部消息类型，微信群禁用文件、微博群仅支持文本与表情（课程简化口径），文本长度上限分别为 8000、5000、1000 字符，引用回复在 QQ 与微信支持而微博不支持。

### 3.4 UI 设计

界面按真实即时通信客户端的操作路径组织：选择自然人与服务、账号中心（开通与登录）、群大厅（浏览与加入官方群）或创建（建群与临时讨论组）、会话内操作，通讯录用于好友与关注管理。全部操作项均为数字键，0 统一为返回上级或进入更多操作，列表型界面的功能键按列表长度动态编号；底部状态条显示每次操作的成功或失败原因，失败原因按规则链给出中文说明；文本输入直接回车即取消，解散群需二次确认。排版由独立模块统一负责：结构固定为「标题栏、键值卡片、小节、对齐菜单、状态条、提示行」，按显示宽度对齐；每帧先缓冲，再按终端可视尺寸裁剪后整帧重绘，因此输出行数与每行宽度都不超过终端可视范围。此外提供自动演示入口，按四段演示群组管理与平台差异、多产品账号与登录联动、好友与群注册表、群消息平台差异，每项校验用「期望成功」或「应失败」包装，结束时输出自检汇总。

### 3.5 相关技术讨论

**持久层使用**：持久化能力由容器自身提供，在构造时读入、析构时写回，业务代码与纯领域对象都不承担 I/O；选择行式文本而非结构化格式，便于逐行解析、坏行跳过与人工查看。**多线程**：本设计有意保持单线程——单机内存模型下所有业务都是同步调用，不存在共享状态的并发访问，引入线程只会带来加锁与竞态的额外复杂度。**容器的使用**：群成员表用以用户 ID 为键的哈希表，成员唯一性由键天然保证、插入与查找平均为常数时间；消息、群列表与好友列表用顺序容器保持插入顺序；已开通与在线平台集合用有序集合去重并按平台顺序展示；共享所有权用共享智能指针表达，授权上下文对群则使用非拥有裸指针避免循环引用；「可能无值」的返回值用可选类型表达。容器的封装原则是成员容器不向业务层暴露可写引用。**字符串与中文编码**：源码与运行期字符串统一为 UTF-8，界面的截断、折行与补空格按显示宽度计算，并对中文环境下按全角渲染的标点按两列高估，只会让折行略早而不会溢出。**跨平台处理**：单键读取在 Windows 使用控制台接口、在 POSIX 临时关闭终端的规范模式与回显，屏幕重绘、尺寸获取与中文输出同样由少量适配代码集中处理，三平台共用同一套业务代码。

## 四、总结与体会

### 4.1 难点问题讨论与解决方案

第一，全员禁言与撤回的约束最初在两个平台策略中各自实现，而成员关系中的禁言标志没有被任何检查消费，导致单员禁言实际失效；解决方法是新增公共状态约束步骤，把两平台一致的规则上提到父类。第二，微信邀请规则一度与任务书口径矛盾（文档写「管理员以上」而任务书要求仅群主为特权账号），最终以任务书为准统一为仅群主可邀请与设置全员禁言，并同步修改策略实现、测试用例与演示文案。第三，撤回时间窗无法在手动测试中触发超时分支，因此让消息实体支持注入发送时刻，在演示中构造窗口外发送的消息复现超时。第四，群主可直接退群会使群处于无主状态，因此拒绝群主退群并补充测试用例。第五，界面曾出现「每按一次键就多跳一段」的偶发缺陷，排查后确认根因是输出量没有与终端尺寸对齐；改为整帧缓冲并按终端可视尺寸裁剪后问题消失，且「输出行数不超过可视行数」成为可断言的不变量。

### 4.2 程序设计的优点与不足

优点在于：平台差异被多态消化，群聚合根中没有任何平台分支；公共授权流程由模板方法固定，避免子类复制粘贴导致的规则遗漏；不变量集中维护，外部无法绕过聚合根修改状态；角色归属正确，同一用户在不同群可有不同角色；任务书条目被落实为可执行的断言。不足在于：系统为单机内存模型，没有网络通信、数据库与真实平台接口；QQ 点对点 TCP 通信为选做项，本次未实现；消息能力与撤回时间窗等均为课程简化口径；断电保存覆盖开通情况、好友与群注册表三类数据；界面为控制台实现，且有意保持单线程。

### 4.3 收获与展望

最主要的体会有三点。第一，面向对象首先是「职责划分」，其次才是语法特性；真正让代码变清晰的是把「群的状态」「授权流程」「平台差异」三件事分开，而不是把所有类都继承自同一个基类。第二，「相同」比「不同」更值得抽象：平台差异只占少数规则，若把判断整体下放，重复的公共逻辑迟早会不一致，用模板方法固定公共流程、只留一个平台差异覆写点，是本次设计中收益最大的决定。第三，文档、测试与实现必须同步：把任务书条目做成可执行的断言后，改动引起的回归会立刻暴露。后续可推进的方向包括补齐选做的点对点网络通信、在接入真实服务时重新设计并发模型、把行式文本存档升级为结构化格式，以及用图形界面替换控制台交互层以验证表现层的可替换性。
