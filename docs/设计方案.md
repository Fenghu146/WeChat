> 范围：吉林大学软件学院《面向对象程序课程设计》· 2025-2026 第 1 学期

## 1. 问题域与数据模型

模拟腾讯统一社交平台的**账号体系**：一个用户可开通多个"微X 服务"（QQ / 微信 / 微博 …），各服务共享部分账号与好友体系、群规则各异。

**三类核心实体：**

| 实体 | 关键字段 | 备注 |
|---|---|---|
| 用户 | 号码 ID、昵称、出生时间、T 龄(申请时间)、所在地 | 号码 ID 唯一 |
| 服务账号 | 所属服务(QQ/微信/微博)、开通时间、登录状态 | 见 4.4 绑定规则 |
| 群 | 群号(1001–1006 等)、成员集合、所属服务、管理模式 | 见 4.3 平台差异 |
| 好友关系 | 双方 ID、来源服务 | 关系可跨服务 |

**ID 共享/绑定规则（决定账号类怎么设计）：**
- 微博 与 QQ：**共享同一个 ID**（一个号码两套服务资料）。
- 微信：**独立 ID**，但可与某个 QQ 号**绑定对应**。
- 结论：账号信息与"服务开通/昵称/所在地"要分开建模，靠 **绑定关系表** 关联，而不是把字段硬塞进同一个类。

## 2. 总体架构（分层，依赖单向向下）

```
┌─────────────────────────────────────────────┐
│ 表示层  main()  数字菜单 + 功能演示用例       │
├─────────────────────────────────────────────┤
│ 门面    Platform 统一入口：初始化/load、菜单分发 │
├─────────────────────────────────────────────┤
│ 领域    服务账号族 / 用户 / 群 / 好友          │
├─────────────────────────────────────────────┤
│ 容器    UserManager / GroupManager /          │
│         FriendManager（存容器 + 提供接口操作）  │
├─────────────────────────────────────────────┤
│ 持久化  FileStore：load() 启动读入，save() 析构写回 │
└─────────────────────────────────────────────┘
```

- 上层只依赖下层接口（面向接口编程，层次 ③ 的"接口保护"）。
- 所有数据在**容器类**中登记，管理器之间通过接口协作，main 不直接摸数据。

## 3. 类设计清单（每个类独立文件，类名带作者缩写）

> 命名纪律（诚信分）：**每个类单独一个文件；类名以作者姓名缩写结尾**。
> 老师示例：张三 设计的 QQ 信息类 = `TencentZhS`（前缀看齐平台风格 + 姓名缩写）。
> 下文 `[缩写]` 即"作者姓名缩写"，提交前各成员替换成自己的。

### 3.1 抽象 / 基础层（建议集中定接口，各组员实现自己负责的部分）

| 建议类名 | 职责 | 关键接口（示意） |
|---|---|---|
| `BaseInfo_[缩写]` | 基本信息通用成员（ID/昵称/时间等）| `getId()` `setNick()` … |
| `IAccountLink`/`BindingTable_[缩写]` | ID 共享与绑定映射 | `bindQQ2WeChat()` `sharedId(service,id)` `weChatIdOf(qqId)` |
| `IFriendOp` | 好友操作接口 | `add/del/update/query` `commonFriends(a,b)` `recommend(fromSvc,toSvc)` |
| `IGroupOp` | 群操作接口 | `join/quit/kick/listMembers` `changePolicy(newType)` |
| `IStore` | 持久化接口 | `load(store)` `save(store)` |

### 3.2 服务账号族（体现继承 + 多态，层次 ③④ 的主战场）

```
PlatformAccount_[缩写]（抽象基类：服务类型、开通态、登录态、抽象"特色入口"）
├── QQAccount_[缩写]      // 共享ID；群可申请加入/可设子群/管理员制
├── WeChatAccount_[缩写]  // 独立ID可绑定QQ；群仅邀请加入/仅群主特权
└── WeiboAccount_[缩写]   // 共享ID（与QQ同ID）；轻量群（可并到通用）
```

- 多态入口示例：`virtual bool canApplyJoin() const`、`virtual bool allowSubGroup() const`、`virtual vector<role> privileges() const` —— 平台差异由子类给出，调用方无需 if-else 判断服务类型。

### 3.3 群管理（重点：管理模式与成员数据分离）

**为什么分离：** 题目要求"在群成员数据不受伤害的前提下，动态变换为其他类型群的管理特色"。若把"群类型"写成 if/else 硬编码在 Group 里，切换要重建/迁移成员，容易"伤数据"。正确做法——**策略（Strategy）模式**：

```
Group_[缩写]          // 数据本体：群号、成员集合、owner
  - 成员：Member（账号ID、角色 role{群主/管理员/普通}）
  - 持有 policy_: IGroupPolicy_[缩写]

IGroupPolicy_[缩写]   // 抽象策略：同一套成员数据上的"玩法"
├── QQPolicy_[缩写]      // 可申请加入、可建讨论子群、有管理员
└── WeChatPolicy_[缩写]  // 仅被推荐加入、无子群、仅群主特权
```

- **切换管理模式 = 换 `policy_` 指针**，`Group` 内成员集合原样保留 → 精确满足题目 6(4)。
- 讨论子群：QQ 独有，`Group` 上可选挂 `children_(子群列表)`（用 isSubGroup 标志位区分），微信策略下该能力被禁用即可，不必删数据结构。

### 3.4 好友与用户

| 类 | 职责要点 |
|---|---|
| `User_[缩写]` | 聚合：基本信息 + 开通服务集 + 好友列表 + 群列表 |
| `UserManager_[缩写]` | 全局用户注册表，`unordered_map<ID,User>`，按 ID 增查 |
| `FriendRelation` | 一条好友关系（双方 ID + 来源服务） |
| `FriendManager_[缩写]` | 好友增删改查；`commonFriends` 求交集；`recommend` 跨服务推荐（依赖绑定表判断是否同一人） |

### 3.5 登录 / 开通（对应题目 4、5）

| 类 | 职责 |
|---|---|
| `ServiceCenter_[缩写]` | 记录每个用户"开通了哪些服务"；登录一个 → 其余置为"已确认自动登录/开通态" |

### 3.6 main 与集成

- `main.cpp` 只做：初始化（load 文件）→ 打印数字菜单 → 分发到 Platform。
- `Platform_[缩写]` 编排题目 6 要求的演示步骤（见 §5）。

## 5. 文件持久化设计（层次 ⑤(2)）

- **格式**：文本文件、易读易改，每类实体一种文件 + 简单分隔（如 `|`），头行写列名，示例：

```
data/friends.txt
  uidA | uidB | fromService
data/groups.txt
  groupNo | service | policy | ownerId | members(uid:role,uid:role,...)
data/services.txt
  userId | service | openedAt
```

- **时机**：`FileStore::load()` 在 main 开头（容器实例化时读入）；各 Manager **析构** 或程序退出前 `save()` 写回 → "断电保存"。
- **可扩展**：预留 `IStore` 接口，将来换二进制/数据库不破坏上层（契合层次 ⑤(3)）。

## 9. 风险与提醒

1. **命名必须带自己缩写**（诚信分，最容易翻车点）。
2. **别在 Group 里 if-else 分平台**——用策略，切换才无损（§3.3）。
3. **TCP / 可视化是选做或不考核**，别投入过多；优先把动态群模式做干净。
4. 微信独立 ID 与 QQ 绑定的映射关系要提前定数据结构，它是好友跨服务的基础。
5. 集成前各分支先各自编译跑通；接口按 3.1 约定，改动跨目录时提前在群里同步。
